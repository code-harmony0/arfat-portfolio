The product

Zonesso is a consumer marketplace for buying and selling cars in Dubai. People browse and filter listings, post their own car, chat with or call sellers, save favourites, pay to promote an ad and get notified about offers.

The brief

The mobile app has to carry the whole marketplace, on iOS and Android, in Arabic and English. I was the only mobile engineer, so architecture, payments, testing and every release were mine to decide, and mine to live with.

How I read it

A marketplace is decided by three screens. Listings have to feel fast, because every visit starts there. Posting an ad has to feel easy, because supply is the product. Checkout has to be correct every time, because it handles real money.

The code history agrees: listing, search and detail screens are among the most-edited in the repo. So I put structure around those three before adding anything on top.

Where I sit in the system

  • I own: the React Native app on iOS and Android, with its payments, testing and release pipeline.
  • I grew into: the Next.js website and the admin dashboard: server-side rendering, Core Web Vitals, bundle size and image pipelines.
  • I touch lightly: the NestJS API, for the changes the app and the web need.

Around the app sit a public web app, an admin panel and two NestJS APIs. They live in separate repositories, so a store release, an SEO release and an internal-tool release never block each other.

Decisions, and why

Server state and app state, kept apart
TanStack Query owns everything that comes from the API: caching, refresh, invalidation. Jotai owns what does not: filters, session, language, theme, notification intent.Screens that fetch and cache in their own way show the same data differently.
Optimistic UI only where the server checks the result
A payment or an edit can show success quickly, but the app then invalidates the affected caches (my ads, packages, listings) and takes the server answer.A marketplace must never show "paid" for something the server has not confirmed.
Five payment methods behind one boundary
Stripe Payment Sheet, Apple In-App Purchase, Apple Pay, Samsung Pay and N-Genius all sit behind one checkout. VAT is computed in one place, with unit tests on the maths and on the payment summary screen.The checkout screen should not know which rail it is using, and money logic should be the most tested code in the app.
Posting an ad is a guided flow
Four steps: location, details and photos, plan, payment summary. Each step has one job and can be tested alone.One long form kept needing fixes in different places.
Listing cards stay light
FlashList for long lists, tuned render windows, and one cached image per card instead of many.Listings are the highest-traffic screen, so they get the strictest budget.
A React Native upgrade run as a cleanup
The move from 0.75 to 0.81 and React 18 to 19 was also the moment to delete what the upgrade made unnecessary: 762 files to 559, 170 dependencies to 120, 53,900 lines to 33,000.With one engineer, every line and every package is something I maintain. Less is cheaper to change.
Keep control of the native build
Three Gradle product flavors, Hermes and ProGuard release builds, Fastlane lanes for both stores.Store releases are where mobile projects go wrong, so I made them repeatable.

Hard problems, and the fix

  • Notification taps that arrived before the app was readyAdded deep-link retry logic, so a tap on a push notification during a cold launch still lands on the right screen.
  • Cold starts that waited on storageLoaded the four critical values in parallel with Promise.allSettled and put a 100-entry LRU cache with tiered TTLs over device storage.
  • Apple In-App Purchase breaking on iOS 18Upgraded react-native-iap to v13, patched it for iOS 18 compatibility and fixed the account token to use a UUID.
  • An App Store rejectionApple rejected a build over App Tracking Transparency compliance and in-app-purchase discoverability. I fixed both.
  • Samsung Pay on release buildsWrote explicit ProGuard rules for the Samsung Pay SDK so it survives release shrinking.

How I run it

  • Releases are commands. Fastlane lanes bump the version, build, upload to Google Play and App Store Connect, and send test builds to Slack.
  • A gate before every build. A pre-build script runs tests and static analysis, and another checks that the screens I test have stable test IDs.
  • CI runs the app. Bitbucket Pipelines runs lint, type checks, unit tests and Android end-to-end tests on an emulator (Jest, Detox, Appium), with a full run and a faster priority-only run.
  • Big features start as a written plan. Background image upload, the listing image carousel and image-upload improvements each have a plan in the repo before the code.
  • Decisions are written down. An architecture document records what was chosen and why, so the next engineer can disagree with evidence.

What I shipped

The app on the App Store and Google Play, the CI and release pipeline behind it, and the website beside it.

The upgrade numbers are a snapshot right after the migration. Feature work has grown the app since, as it should. What changed is the cost of that growth.
